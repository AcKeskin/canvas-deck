# Spec — canvas-engine (v1)

## Problem
canvas-deck needs every slide to be an infinite canvas where you can draw, write and place content, then move around it freely while presenting. This is the base every other module sits on (vision canvas-deck v1), and the library choice shapes editing-tools, presenter and performance.

## Goals
- One infinite canvas per slide, rendered inside the Obsidian deck view.
- Built on Excalidraw (MIT).
- Each slide has a 16:9 start frame: what the audience sees first. Content can go past it.
- Saved views per slide: named camera targets you step through in order.
- Camera API other modules call: go to frame, go to view, free pan/zoom, read-only mode.
- Both styles per object: hand-drawn or clean lines.
- Vault images on the canvas.
- Smooth with ~2,000 objects on a slide.
- Pen, touch and mouse input, with pressure.

## Non-goals
- Own tool UI beyond what Excalidraw provides (editing-tools owns that layer).
- Slide switching, ordering or speaker notes (slide-navigator).
- File IO (deck-store); the engine hands over and takes slide data only.
- Note embeds (note-embeds module renders into the engine later).
- Real 10,000+ object diagrams.
- Animation timelines.

## User-facing behavior
- Opening a slide shows its 16:9 frame fitted to the view.
- The user can pan and zoom anywhere, in edit and present mode.
- Each object can be set to sketch or clean style.
- The user can save the current camera as a named view and reorder views.
- Going to a view animates the camera there; "home" returns to the frame.
- Dropping or pasting a vault image puts it on the canvas, linked to the vault file.
- In present mode, the canvas is read-only but still pans and zooms.

## Technical approach
- Embed the Excalidraw React component inside an Obsidian view.
- Style per object maps to Excalidraw's roughness setting (sketch vs clean).
- 16:9 frame and saved views are stored as slide metadata next to Excalidraw's scene data, not as drawn objects.
- Camera moves use Excalidraw's scroll/zoom API, with an animation layer on top.
- Images reference vault paths rather than embedding copies, so the vault stays the source of truth.
- Read-only mode uses Excalidraw's view mode.
- Performance check: a generated 2,000-object test slide.

## Constraints
- Must run in Obsidian desktop and mobile; no Node-only APIs.
- Bundle size: Excalidraw is large; keep it to one bundled copy.
- The user has no iPad; mobile is verified on desktop with Obsidian's mobile emulation.

## Grounded context
- vision canvas-deck v1, module canvas-engine: owns scene objects, rendering, camera, hit-testing, start view; does not own tool UI, slide switching or file IO.
- Memory canvas-deck-vision: slides are separate canvases, not Prezi-style; pen input from day one.

## Open questions
- Does the Excalidraw scroll/zoom API allow smooth animated camera moves, or does that need a custom tween?
- How do vault image links survive a renamed or moved image file?
- Do we conflict with the existing Obsidian Excalidraw plugin if both are installed (file types, shared React)?

## Verification criteria
- `npm run build` and `npm test` pass. Tests save a slide with frame, saved views and objects, load it, and compare equal.
- A generated 2,000-object slide holds 50+ fps on desktop and 30+ fps with mobile emulation, measured with the dev tools performance panel while panning and zooming.
- Going to a saved view lands on that view's exact bounds; home lands on the 16:9 frame.
- Synthetic pointer events with different pressure give strokes of different width. A dropped vault image is still visible after restarting Obsidian.
